Reference Why VMC on AWS

The comparison the "Business case documented" item below asks you to make explicit — against staying self-managed on-prem, and against re-architecting straight onto cloud-native compute. VMC's pitch is specifically the middle path: AWS's infrastructure and operating model, without giving up the vSphere/NSX platform (and skills, and app compatibility) you already run.

i
In short: self-managed on-prem gives you full control, but every operational burden — procurement, patching, hardware failure, a second DR site — is yours to carry, and that overhead scales with fleet size. Refactoring onto cloud-native compute trades that control for a genuinely elastic, provider-managed platform, but the re-architecture itself commonly runs over budget and behind schedule (see the industry figures further down this tab), with a long, expensive stretch of running two platforms in parallel before a single production workload cuts over. VMC sits in between: the same vSphere/NSX/vSAN platform your team already operates, run end-to-end by VMware — hardware, patching, hardened baseline, even burst capacity for maintenance windows — deployed in hours and migrated in days via HCX, so that parallel-running window (and its cost) stays short. The tables below go dimension by dimension; the diagram right after this makes the cost-of-delay point on its own.

Schematic, not measured cost data — bar lengths illustrate the relative durations already cited in the cards on this tab (SDDC deploy/HCX timing above; McKinsey-sourced re-architecture schedule figures in the card below), not a dollar figure. Wider dual-running window = longer stretch of paying full price for both platforms at once, assuming a roughly constant run-rate on each side.

i
Coordinated disclosure works differently at fleet scale. When a vulnerability affecting ESXi, vCenter, NSX, or vSAN is disclosed, VMware remediates every VMC on AWS SDDC across the entire fleet before the patch or advisory goes out publicly. That closes a window self-managed estates live in by default: once a patch ships, threat actors routinely reverse-engineer ("diff") it to build a working exploit within days, then go hunting for whoever hasn't applied it yet — that's the usual "N-day" exploitation race. On VMC, there's no unpatched estate left for that exploit to land on; every SDDC is already fixed by the time the vulnerability becomes public knowledge. Confirm the current disclosure-to-remediation practice against VMware's own security advisories process before quoting it as a hard guarantee — see the card footer below.

Every host is single-tenant, dedicated to you — never shared with another VMware customer's workloads. The performance you size for on the Design & Size tab is the performance you actually get, no multi-tenant contention to budget headroom against on top of your own workloads' demand.
Patch & CVE exposure Your own patch cycle and change windows — the usual reason estates run years behind on ESXi/ vCenter versions. Provider-side patching for managed PaaS components; you still patch anything you run yourself (containers, EC2 guest OS). VMware patches ESXi, vCenter, NSX, and vSAN on its own cadence — no hypervisor maintenance window to schedule, and no risk of being the estate still running an EOL build nobody got round to upgrading. A non-billable host is temporarily added to the cluster for the duration of the patch so your configured resilience level (e.g. N+1) never dips — you're never asked to run under-covered while a host is pulled for maintenance, and you don't pay for that headroom either.
Security & compliance posture Physical security and every compliance attestation (ISO 27001, SOC 2, PCI DSS, etc.) is your own program to build, run, and prove. Inherits the provider's physical/compliance posture, but the security model itself changes — IAM, security groups, and per-service configuration are a genuinely new set of things to get right. Inherits AWS's physical and compliance posture and keeps the NSX DFW micro-segmentation model the team already knows; vSAN encrypts data at rest by default. Confirm current attestations and the published SLA on VMware's own trust/status pages before quoting either as fact.
Vulnerability disclosure & patch-gap exposure Once a patch or advisory is public, you're racing your own change-control process against attackers who reverse-engineer it — the estate stays a known, addressable target for however long that takes. Provider-managed components get the same fleet-wide protection VMC offers below; anything you operate yourself (guest OS, containers, self-hosted services) runs the same race as on-prem. See the callout above — the fleet is remediated ahead of public disclosure, so there's no still-vulnerable VMC estate left for a reverse-engineered exploit to target.
Host & vCenter administrative access Full root on ESXi and admin on vCenter — powerful, but every one of those credentials is an insider-threat and phishing target, and nothing stops a host quietly drifting out of hardened baseline one hand-tuned setting at a time. You hold full admin on whatever compute/IAM layer you build — same trade-off as on-prem, just moved up a level to cloud-native services instead of the hypervisor. No customer ever gets SSH/root on ESXi or the vCenter appliance's underlying admin account — VMware operates the hardened baseline directly. That's not just fewer credentials to leak: it's what makes the fleet-wide patch guarantee above actually enforceable, since no host can drift out of a config VMware doesn't have to fight a customer's own changes to remediate.
Compliance audit scope The full stack — physical security, hypervisor configuration, storage, network — is in scope for every attestation and audit you carry (PCI DSS included): you have to evidence controls on layers most cloud-hosted competitors never have to touch. Provider infrastructure drops out of scope, but everything you configure yourself (IAM, security groups, service configuration) is now new attack surface an assessor has to evaluate. Because no customer can touch the hypervisor or vCenter admin account, that whole layer is verifiably out of the customer's control boundary — for a PCI DSS cardholder-data-environment assessment in particular, that's real scope reduction: the assessor evaluates what you actually operate (guest OS, application, workload NSX policy), not a hypervisor you never had access to misconfigure. Confirm current attestations (PCI DSS, ISO 27001, SOC 2) on VMware's own compliance pages — which controls fall on VMware's side of the line is documented there, not here.
DR / HA A second site is capex — build, run, and patch an entire second stack to get it. Native multi-AZ/multi-region patterns are available, but only once the re-architected app actually supports them. A stretched cluster spans two AZs for HA with no second site to build; VMware Live Recovery or a second SDDC covers DR proper — see the Compliance checklist item below for when this is a hard requirement, not a nice-to-have.
Cost model Capex-heavy and lumpy (refresh cycles), on top of the ongoing opex of running it. Consumption-based once live, but the re-architecture itself is a large, hard-to-size one-off cost that isn't on any cloud bill. Opex subscription, sized against the estate you already have — see the Cost & subscription planning card below for the actual numbers.
Networking to stand up Physical VLANs/routing already exist, but a refresh still means re-cabling and a live cutover of all of it. A full redesign from scratch — VPCs, subnets, security groups, load balancers, DNS — with a genuinely different mental model, not a port of existing config. NSX segments and the DFW/MGW/CGW model carry straight across unchanged; only the AWS-side pieces (Connected VPC, route tables, Direct Connect/Transit Connect) are new — see the AWS networking primer card below for exactly what's different.
Existing tooling & integrations Backup agents, monitoring, VCF Operations, and CMDB integrations are already wired in. Most need replacing or re-integrating with cloud-native equivalents (native backup, CloudWatch, a different monitoring agent) as part of the same project. The same vCenter-pluggable tooling keeps working with little to no change — validate your specific backup product against the VMC-supported list on the Optimise tab rather than assuming every on-prem tool is covered.
Elasticity / scale flexibility Fixed until the next refresh cycle — adding real capacity takes months, not minutes. Elastic by design and the strongest card cloud-native holds — pay only for what's actually running, scale to zero if idle. Elastic DRS adds/removes hosts automatically, but only within a pool of subscriptions you've already bought — scaling past that pool still needs a new host subscription purchased in advance. Genuinely less elastic than native compute; don't oversell this one.
Vendor & support model Server OEM, storage OEM, network vendor, and VMware licensing are separate relationships — you integrate across all of them when something breaks. AWS supports the infrastructure; you still own support for everything you built on top of it. One Broadcom support contract covers the SDDC layer end-to-end — hosts, hypervisor, vSAN, NSX — with AWS's infrastructure underneath it, invisible and not something you file a ticket against directly.
Exit / portability Workloads stay wherever the hardware is — moving them anywhere is its own project. The hardest of the three to leave once workloads are rebuilt against provider-specific managed services — that's real lock-in, not a talking point. Workloads stay in standard OVF/VMDK format throughout — HCX (or a plain vMotion) can move them back on-prem or to another vSphere-based cloud just as easily as it moved them in. Lower lock-in risk than a cloud-native rebuild, mechanically, not as a claim.
Why the operational model can be cheaper — even when the subscription line itself isn't

The subscription price rarely beats depreciated hardware dollar-for-dollar in a straight sticker-price comparison — that's not where the saving is. It's in the operational overhead that a self-managed estate carries around that price, most of which never shows up on the hardware invoice itself:

i
The man-hours gap widens as you scale. Hardware failure is a numbers game — the larger the fleet, the more failures land on your desk every year, and each one is its own diagnose-RMA-evacuate-replace-revalidate cycle. On-prem, that operational burden scales with host count: a 200-host estate doesn't just have more compute, it has proportionally more failure/support tickets to run, every one of them engineer time. On VMC, none of that reaches you at any scale — VMware detects the failure, evacuates the host, and replaces the hardware without an open ticket in your queue, whether the SDDC is 4 hosts or 400. The engineer-hours a self-managed estate spends on hardware break-fix stays close to flat on VMC as the fleet grows, structurally, not just typically lower — this is the row below where scale matters most.

Absorbed entirely by VMware. That engineer time redirects to application and workload work instead of keeping the platform itself alive.

The operational burden grows with host count, not just the compute it delivers. Hardware failure, diagnosis, RMA, and replacement are VMware's responsibility end-to-end at any scale — the engineer-hour cost to you stays effectively flat as the estate grows, instead of scaling with it the way it does on-prem.
Hardware-refresh capex projects A 6-12+ month project every 3-5 years — procurement, data migration, cutover risk — often with contractor/consulting spend stacked on top of internal time. Eliminated. Broadcom replaces the underlying hardware without a customer-run project or a planned downtime window.
Idle, over-provisioned capacity Capacity bought years ahead of need, plus N+1/N+2 redundancy, sits mostly idle — still costing power, cooling, and depreciation the whole time it isn't used. Elastic DRS buys closer to actual demand on a shorter cycle — genuinely less stranded capital, though not instant or unlimited (see the Elasticity row above).
A second (DR) site Duplicates every cost above just to sit mostly idle, plus its own patch cycle and failover testing burden. A stretched cluster or VMware Live Recovery replaces a capex site with an opex line — no second physical stack to build, run, and keep in parity.
Patch-lag risk Estates that fall behind on patching — because a downtime window is hard to get approved — carry a real breach/outage risk that rarely appears on a budget line until it's realized. Removed structurally: VMware patches ESXi/vCenter/NSX/vSAN on its own cadence, with no maintenance window for you to schedule or keep deferring.
Maintenance-window resilience capacity To patch a host without dropping below your resilience target (e.g. N+1), you have to own and power that spare host year-round — capacity that sits idle except for the rare window it exists for. VMware temporarily adds a non-billable host to the cluster for the duration of a patch to hold your resilience level, then removes it once the maintenance completes — you never buy, own, or pay for that headroom yourself.
Multi-vendor incident coordination Server OEM vs. storage OEM vs. network vendor vs. VMware licensing — cross-vendor finger-pointing during an incident extends time-to-resolution, and downtime has its own cost. One Broadcom support contract covers the SDDC stack end-to-end, cutting the coordination overhead exactly when it matters most.
Facilities Power, cooling, colo/rack space, and eventual decommissioning/e-waste are a fixed cost line regardless of how busy the estate actually is. Folded into the subscription price — disappears as a separate line item to track and pay.

None of this means the subscription line item is cheaper than depreciated hardware — it often isn't. The saving shows up in total cost of ownership once labour, capex-project cost, idle capacity, and facilities are added back to the on-prem side — which is exactly what the "on-prem run-rate baseline" and "TCO comparison" checklist items below are for. Skip either one and you're comparing a subscription invoice to a hardware invoice, not a real TCO.

Who operates what, in one line: physical hosts, the hypervisor, vSAN, and the NSX control plane are VMware's responsibility; guest OS, applications and data, workload-level NSX policy, backup/DR configuration, and your own AWS IAM are yours — the same split as the shared-responsibility model referenced in the AWS networking primer below. On-prem, all of it is yours.

Fits well when: a data-centre exit or hardware refresh is forcing a near-term date; most of the estate is COTS/legacy apps that don't justify a rewrite; the team's depth is vSphere/NSX rather than cloud-native; or DR/compliance needs a fast, low-risk lift rather than a ground-up redesign. Think twice when: the goal is a genuine cloud-native transformation the application footprint already supports (VMC becomes an expensive detour on the way there); the estate is small enough that on-demand native compute is simply cheaper at that scale; or the workload needs to scale to zero — the subscription model always has a minimum host floor to pay for, unlike serverless/native compute.

!
This isn't a rare outcome — it's the industry norm. A widely cited McKinsey survey of roughly 450 CIOs and IT decision-makers (2021) found 75% of cloud migrations ran over budget and 37–38% ran behind schedule, with an estimated $100 billion in wasted migration spend projected industry-wide over the following three years. These figures describe cloud migration generally, not VMC specifically, and are reported here via secondary sources (the original McKinsey report could not be fetched directly to confirm methodology first-hand) — treat as directionally credible industry signal, not a project-specific guarantee, and verify current figures before citing them in a business case.

These overruns aren't random bad luck — they trace back to a small set of recurring root causes, most of which are specific to re-architecting an application for cloud-native, not to migration in general. VMC avoids most of them structurally, by not requiring a re-architecture in the first place.

Root cause of overrunWhy it hits a cloud-native re-architectureHow VMC avoids it
Every dependency becomes a design decision RDMs, WSFC clusters, physical device dependencies, and vendor licensing terms (Oracle's cloud stance in particular) each force an architectural choice mid-project — discovered as blockers during the build, not scoped before it starts. HCX moves the VM as-is — same OS, same binaries, same dependencies. Run the RVTools analyzer up front (Assess tab) to surface blockers before wave planning starts, not mid-migration.
Undocumented dependencies surface late A re-architecture forces every integration point (what talks to what, on which port, how) to be rediscovered and redesigned — legacy apps routinely have dependencies nobody wrote down. Nothing about the app or its immediate network context changes, so undocumented dependencies that would break a redesign simply keep working — there's nothing to rediscover.
Skills gap forces expensive contractors Cloud-native architecture, IAM, and networking are frequently skills the team doesn't have yet — closing that gap with contractors extends both cost and timeline, and the knowledge often leaves with them. Needs the same vSphere/NSX/vSAN concepts the team already has, at a day-2 operate level (see the Skills required row above) — a materially smaller gap to close.
No safe rollback once underway Once code, data model, and infrastructure have all changed together, reverting to the on-prem original isn't simple — a struggling project faces sunk-cost pressure to push forward rather than stop. Workloads stay in standard OVF/VMDK the whole time (see the Exit/portability row above) — a wave can be paused, tested, or reverted without an irreversible one-way rebuild behind it.
Non-production spend accrues invisibly Dev/test/staging and proof-of-concept environments run for the entire re-architecture period — sometimes months to years — before a production cutover, and rarely show up as one clean budget line (see the Cost incurred before any workload is live row above). No re-architecture period to carry non-production spend through — HCX/network-extension work is typically days, not months, so the same risk exists but the window it can compound in is far shorter.
Big-bang cutover risk A changed application architecture often can't be cut over gradually — the redesign forces large, all-or-nothing go-live events with everything riding on one cutover window. HCX supports wave-based migration — a handful of non-critical VMs first (see the "Test migration of 2–3 non-critical VMs" checklist item), then subsequent waves by application and criticality, each with its own rollback plan.

Reference Stretched Cluster 1 + non-stretched clusters

A stretched SDDC doesn't have to mean every cluster in it is stretched. Cluster 1 (where vCenter, NSX Manager and NSX Edge always live) is the common candidate to stretch for AZ-level protection of management and your most critical workloads — additional clusters in the same SDDC can stay single-AZ for anything that doesn't need that level of infrastructure resilience, and that split is where the real cost saving sits.

DimensionStretched Cluster 1 + non-stretched clustersTwo non-stretched clusters, app-layer HA instead
What it is One SDDC; Cluster 1 spans two AZs (mirrored, with an off-cluster witness); additional clusters in the same SDDC stay single-AZ. No stretched cluster at all — two ordinary single-AZ clusters (in different AZs, or split across two SDDCs/regions for more separation), with the application itself providing failover: a clustered app tier behind a load balancer, DB replication/Always On, or queue-based decoupling.
RAID/storage-efficiency impact Cluster 1 is locked to RAID-1 mirroring (VMC doesn't offer erasure coding on a stretched cluster) on top of the cross-AZ mirror itself — the least storage-efficient combination available. The non-stretched clusters are unaffected and can still use RAID-5/6. Both clusters get full RAID-5/6 erasure-coding efficiency and no synchronous cross-AZ mirror overhead — meaningfully less raw storage for the same usable capacity than a stretched cluster sized to hold the same workload.
Best for Workloads that genuinely need infrastructure-level AZ failover and have no HA of their own — put those on Cluster 1; put dev/test, batch/analytics, and anything with its own clustering on the non-stretched clusters instead of paying the stretch tax for all of it. Applications that already ship with their own HA/clustering model — infrastructure-level stretching is redundant spend on top of what the app already does for itself.
Cost impact Only the stretched cluster pays the storage-doubling-plus-RAID-1-only tax; the rest of the estate sizes at normal single-AZ efficiency, so total estate storage footprint and host count come in lower than stretching everything. No cluster pays the stretch tax at all — the lowest total storage footprint of the three patterns on this page, at the cost of the application (not the infrastructure) carrying the HA logic. Not appropriate for workloads that can't provide that themselves.

Reference AWS networking for VMware admins

The single biggest mental-model shift: the SDDC is not "in" your AWS account. VMware provisions and operates it inside a VMware-owned AWS account that you never see in your own console — you won't find its hosts, ENIs, or subnets in EC2 inventory. Your own AWS account only holds the Connected VPC (and, optionally, a Direct Connect or Transit Gateway attachment) that the SDDC plugs into. VMware manages the hypervisor, vSAN, and the NSX control plane; you manage the guest OS, workload networking policy, your Connected VPC, and your own AWS IAM — the same split of responsibility as on-prem, just with a different line drawn.

On-prem / vSphere conceptAWS / VMC equivalentWhat's different
Physical site AWS Region + Availability Zone A single-AZ SDDC's hosts all sit in one AZ — one site, not automatically resilient across sites. A stretched cluster spans two AZs in the same region for host/AZ failure protection; that's HA, not DR — there's still no cross-region protection without VMware Live Recovery or a second SDDC.
vDS port group / VLAN NSX segment (inside the SDDC) vs. VPC subnet (in your Connected VPC) Two separate address spaces in two separate places. Workload IPs live in NSX segments you create inside the SDDC; the Connected VPC subnet is a different network in your own AWS account, used mainly for the SDDC's native-AWS-service connection, not for workload IPs.
SDDC ↔ VPC data path Elastic Network Interface (ENI), not Direct Connect/VPN The SDDC talks to your Connected VPC over a high-bandwidth, low-latency ENI-based connection that VMware provisions automatically at SDDC creation — this is what gives workloads fast access to native AWS services (S3, RDS, etc.) in that VPC without needing Direct Connect, a VPN, or the internet. Direct Connect/VPN/Transit Connect are for reaching your own network (on-prem or other VPCs), not for this SDDC-to-VPC path.
vCenter SSO / AD-integrated login AWS IAM (your account) + VMware Cloud Console org roles (the SDDC) Two separate identity systems, not one SSO. IAM controls your own AWS account — route tables, the Connected VPC, Direct Connect/Transit Gateway. Cloud Console org roles (Org Owner, SDDC Admin, read-only) control the SDDC itself. Neither is your on-prem AD, though vCenter SSO inside the SDDC can still bind to your existing AD/LDAP over whatever connectivity you build.
vSphere Distributed Firewall (east-west rules) NSX DFW (same idea) — plus two more layers most admins don't expect Traffic also crosses the Management Gateway (MGW) (protects vCenter/NSX Manager/HCX) and Compute Gateway (CGW) (north-south for workloads) — both perimeter firewalls, not east-west. AWS Security Groups are a third, entirely separate firewall layer that only applies inside your own Connected VPC — they have no effect on traffic inside the SDDC.
Static route / L3 gateway config AWS VPC route table entries (and Transit Gateway route tables, if used) The SDDC's management and workload CIDRs must be added as routes in your Connected VPC's route table yourself — VMware doesn't do this for you. A missing route here is the single most common "can't reach the SDDC" support case. Using Transit Connect (vTGW)? The same applies to every Transit Gateway route table involved.
Firewall ACL for internet ingress Public IPs (VMware's own pool) + CGW NAT rules The SDDC has no default internet-facing address. You request Public IPs from VMware's pool (separate from AWS Elastic IPs) and write CGW NAT rules mapping them to internal workload IPs — closer to a traditional NAT/firewall ACL than to anything address-related on the AWS side.
MPLS/WAN circuit to a second site IPsec VPN, AWS Direct Connect, or Transit Connect (vTGW) Pick by bandwidth, latency, and lead time: IPsec VPN stands up in hours but is internet-dependent and bandwidth-capped; Direct Connect is a physical private circuit (weeks of lead time, highest bandwidth/lowest latency, billed separately by AWS); Transit Connect is VMware-managed and is the only supported way to mesh multiple SDDCs together — see the SDDC design section on the Design & Size tab.
DNS forwarders / AD-integrated DNS Route 53 Resolver, or your own forwarding The SDDC does not automatically see your on-prem DNS. Plan conditional forwarding in both directions — SDDC to your on-prem AD zones, and on-prem to whatever the SDDC hosts — before cutover, or workloads resolve nothing on their first boot in the SDDC.

This is a mental-model primer, not a substitute for the authoritative reference — validate specifics against VMware's own Networking and Security guide for VMware Cloud on AWS on docs.vmware.com before you finalise a design.

VCF Operations for Networks (vRNI) doesn't just draw a dependency diagram — it plugs directly into HCX so wave planning stops being manual guesswork. vRNI's Application Discovery and Dependency Analytics groups discovered VM-to-VM traffic into Application Groups — VMs that talk to each other closely enough that they belong in the same wave — then exports each one via HCX's public API directly into a matching Mobility Group, HCX's own migration execution unit (labelled and timestamped so it's clear which groups came from vRNI versus ones an admin created by hand). Post-migration recommendations

What to tighten once the last wave has landed and the estate is running steady state.

i
This list is shorter than the on-prem equivalent, and that's the point. Steady state is where VMC's operating model keeps paying off, quietly, in the background: hardware failure, hypervisor/ NSX/vSAN patching, and the fleet-wide pre-disclosure remediation covered on the Business Case tab's "Why VMC on AWS" card are already handled — they never make it onto this list because they're not your job. What's left below is deliberately everything above that line: security policy, cost tuning, DR configuration, and app-layer housekeeping — the parts of "post-migration optimisation" that stay yours on any platform.
Security
Enable the NSX Distributed Firewall

Move beyond perimeter-only CGW and MGW rules. Enforce micro-segmentation with the NSX DFW so east-west traffic between workloads is filtered too — it's already part of the platform, not a separate micro-segmentation product to evaluate and buy. Start in monitor mode to baseline real traffic before you enforce.

Security
Integrate AWS GuardDuty & Security Hub

Enable GuardDuty on the connected VPC and aggregate findings in Security Hub. Turn on CloudTrail for the cloud org to audit API-level actions, and forward alerts into your existing SIEM.

Cost optimisation
Validate host-type fit at renewal, not before

The subscription commitment (host type, count, a term of at least 1 year) has to be in place before migration — VMC no longer sells on-demand capacity, and subscriptions must be purchased in advance of SDDC deployment or host scaling (an under-subscribed SDDC gets paused within 48 hours, not a grace period to decide). Make that call from this tool's sizing estimate and real on-prem metrics up front, with Elastic DRS burst-host headroom already subscribed for. Once running, use a month of real VCF Operations production metrics to confirm the host type actually matches the workload's storage-to-compute ratio — i3en.metal for capacity-dense estates, i4i.metal for memory-heavy ones, i7i.metal-24xl as the general-purpose default — and feed any correction into the next subscription renewal or additional purchase, since what's already committed doesn't refund mid-term.

Cost optimisation
Elastic DRS & commit planning

Enable Elastic DRS so hosts scale with demand — added at peak, removed in the troughs, against a pool of subscriptions you've already bought. That's still capacity you own, but the add/remove mechanics themselves are something a self-managed estate simply can't do without owning permanent spare hardware for the peak case — VMC turns that into a policy setting instead of a rack. Pair it with AWS savings plans for connected-VPC workloads, and review S3 tiering for any VM backups landing in AWS.

Performance
Adopt vSAN storage policies

Prefer vSAN ESA — it's the default on i4i.metal and i7i.metal-24xl (i3en.metal always sizes as OSA) — and prefer RAID-5/6 erasure coding over RAID-1 mirroring wherever the cluster's host count allows it (RAID-5 needs 3+ hosts on ESA, RAID-6 needs 4+): same protection, less raw capacity spent than mirroring. The exception is a stretched cluster — VMC restricts those to RAID-1 mirroring only, no erasure-coded option is offered. Review vSAN Health and performance dashboards weekly.

Performance
Upgrade VM hardware & Tools

Once migrated, bring VMs up to the latest supported hardware version (vmx-21 on vSphere 8) and current VMware Tools. That unlocks PVSCSI, VMXNET3 improvements, and guest OS optimisations. Schedule it into maintenance windows rather than doing it mid-migration.

Networking
Migrate to Direct Connect

If you started on IPsec VPN, plan the move to AWS Direct Connect with Transit Connect for production traffic. You get predictable latency, higher bandwidth (up to 100 Gbps LAGs), and lower data-transfer costs.

Networking
Unstretch networks & cut over DNS

Once every VM on a segment has moved, remove the HCX L2 extension, repoint default gateways to the SDDC side, and flip DNS records. This stops traffic tromboning through on-prem and frees the network extension appliances for the next wave.

Operations
Automate backups with a validated third-party tool

Not every backup/replication product is validated for VMC — check Broadcom KB 334973 before committing to one. Veeam, Cohesity, Commvault (Metallic), Rubrik, Dell EMC PowerProtect/Avamar/NetWorker, Druva Phoenix, and IBM Spectrum Protect Plus are named there; Zerto is not — VMC on AWS replication support has been on Zerto's own roadmap, unshipped, for years. Define RPO and RTO per tier, automate retention, and test restores quarterly regardless of which tool you land on.

Operations
Implement lifecycle automation

Use VCF Automation for VM provisioning with approval workflows, tagging, and automatic decommission, and drive the SDDC itself from Terraform. This is what stops sprawl and keeps governance enforceable rather than aspirational.

Disaster recovery
Configure VMware Live Site Recovery

Set up VMware Live Site Recovery (formerly SRM, built on vSphere Replication) — VMware's own native, VMC-supported DR path, alongside VMware Cloud DR and Live Cyber Recovery for the ransomware-recovery case. Define protection groups and recovery plans, and test failover monthly. Use a second SDDC in another AWS region for cross-region DR — an opex subscription standing in for what would otherwise be a second physical site to build, power, and keep in patch parity. Third-party replication tools need to be checked against Broadcom's own validated list first — Zerto, for one, doesn't support VMC on AWS as a replication target today.

Disaster recovery
Leverage native AWS services

Connect workloads to AWS-native services across the connected VPC — RDS for managed databases, S3 for object storage, ELB for load balancing, CloudFront for CDN — over the high-bandwidth ENI path the SDDC gets automatically at creation, no VPN/Direct Connect required for this specific traffic. Offloading commodity infrastructure this way reduces the host count you pay for; it's also simply not on the table on-prem without first landing that data in AWS some other way.
